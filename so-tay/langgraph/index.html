LangGraph: điều phối agent bằng graph có state

LangGraph là một framework điều phối mức thấp, đồng thời là runtime, dành cho các agent chạy lâu và có trạng thái (state).[1] Bạn mô tả công việc thành một graph: một state dùng chung, các node làm việc và các edge quyết định bước tiếp theo.[2]

Bài 2/3 trong loạt LangChain · LangGraph · LangSmith. Bài 1 LangChain nói về model, tool, retriever và hàm create_agent. Agent của LangChain được xây trên LangGraph,[19][21] nên bài này là "tầng bên dưới". Bài 3 LangSmith nói về tracing và đánh giá. LangGraph dùng riêng được, không bắt buộc cài LangChain.[1][27]

Vì sao cần graph, không chỉ một vòng lặp while?

Agent cơ bản là model gọi tool trong một vòng lặp tới khi xong việc.[20] Bạn có thể tự viết vòng lặp đó trong vài chục dòng. Vấn đề xuất hiện khi đưa nó vào quy trình thật của doanh nghiệp:

Vấn đề 1

Process chết là mất hết

Vòng lặp tự viết giữ mọi thứ trong RAM. LangGraph lưu một checkpoint của state ở mỗi super-step (mỗi nhịp chạy của graph),[7] nên có thể chạy tiếp sau sự cố hoặc sau khi tạm dừng.[1]

Vấn đề 2

Phải chờ người duyệt

Khoản hoàn tiền lớn cần trưởng nhóm duyệt, có khi tới sáng hôm sau. LangGraph cho graph dừng lại, để người xem hoặc sửa state, rồi chạy tiếp.[1][9]

Vấn đề 3

Luồng vừa cố định vừa linh hoạt

Bước "tra chính sách" luôn phải chạy, còn bước "trả lời khách" để LLM tự quyết. LangGraph cho trộn node viết tay và node do model quyết định trong cùng một graph.[1]

Vấn đề 4

Khó biết agent đã làm gì

Lịch sử checkpoint cho phép xem lại state ở từng bước, chạy lại hoặc rẽ nhánh từ một bước cũ (time travel),[10] và stream được token cùng các update của state trong lúc chạy.[1]

Hình dung bằng một ví dụ đời thường

🗂️ Bộ hồ sơ đi qua nhiều bàn

State là bộ hồ sơ dùng chung. Node là từng bàn làm việc: mỗi bàn đọc hồ sơ, làm phần của mình và ghi thêm vào. Edge là quy định "xong bàn này thì chuyển sang bàn nào".

Hết mỗi lượt, thư ký chụp lại bộ hồ sơ (checkpoint) và cất vào tủ theo mã hồ sơ (thread_id). Mất điện thì hôm sau mở tủ làm tiếp. Cần sếp ký thì hồ sơ nằm trong tủ chờ, không ai phải ngồi canh.

🧭 Workflow hay agent?

Workflow có đường đi định sẵn và chạy theo thứ tự đã thiết kế. Agent tự quyết cách làm và tự chọn tool.[17]

LangGraph dựng được cả hai, và hay dùng nhất là trộn chúng: phần cần kiểm soát thì đi theo edge cố định, phần cần suy luận thì giao cho LLM. Xem thêm khái niệm agent ở trang AI agent và phần "vỏ" quanh model ở trang Harness.

Khi nào chưa cần LangGraph trực tiếp? Nếu bài toán chỉ là một agent gọi tool thông thường, tài liệu LangChain khuyên dùng create_agent. Còn LangGraph dành cho "nhu cầu nâng cao, trộn workflow cố định với agent".[19] Ở phía multi-agent, tài liệu cũng nhắc rằng một agent với đúng tool và prompt thường đã đạt kết quả tương tự.[14]

Phiên bản: tại ngày 2026-11-18, bản langgraph mới nhất trên PyPI là 1.2.22 (phát hành 2026-11-14), giấy phép MIT, cần Python 3.10 trở lên.[28] Bản 1.0 ra ngày 2025-10-22, kèm cam kết không có thay đổi phá vỡ tương thích cho tới 2.0.[21] Trang này dùng tài liệu Python làm tham chiếu chính.

2. Flow: một lần chạy graph đi qua những gì

LangGraph chạy graph theo từng nhịp, mỗi nhịp gọi là một super-step. Cách chạy này mô phỏng theo hệ thống Pregel của Google: các node trao đổi với nhau bằng message. Node chạy song song nằm chung một super-step; node chạy nối tiếp nằm ở các super-step khác nhau.[2]

Mỗi super-step có ba pha: Plan chọn node sẽ chạy, Execution chạy song song các node đó, Update ghi kết quả vào state.[5] Edge quyết định node nào nhận message để chạy ở nhịp sau. Nếu có checkpointer, cuối mỗi super-step state được lưu thành một checkpoint, kèm danh sách node sẽ chạy tiếp (next).[7]

Graph dừng khi không còn node nào được kích hoạt và không còn message nào đang chờ.[2]

3. Cơ chế cốt lõi

Mục này đi qua từng khối của LangGraph theo thứ tự: cấu trúc graph → cách chạy → lưu trạng thái → con người can thiệp → quan sát → memory → ghép nhiều graph → hai cách viết → triển khai.

Muốn thấy một lần chạy cụ thể trước thì nhảy tới mục 4 và mục 5, rồi quay lại đây. Lần đầu đọc, 3.1–3.6 là phần cốt lõi; 3.7–3.11 có thể đọc sau.

3.1 State, node, edge và reducer

State và reducer

State là bản ghi trạng thái mà mọi node dùng chung, thường khai báo bằng một schema có kiểu.[2] Node không sửa thẳng state mà trả về phần update.[3] Mỗi key có một reducer quyết định cách gộp update vào giá trị cũ:

  • Không khai báo reducer: giá trị mới ghi đè giá trị cũ.[2]
  • operator.add: nối thêm vào list.
  • add_messages: nối message mới và cập nhật message cũ theo ID. Khi người duyệt sửa một message, chỉ add_messages sửa được tại chỗ.[2]
class RefundState(TypedDict):
    refund_amount: int                          # ghi đè
    notes: Annotated[list[str], operator.add]   # nối thêm
    messages: Annotated[list, add_messages]     # nối + sửa theo ID

Có thể tách schema input, output và các key riêng chỉ node nội bộ dùng. Lưu ý: các schema này không ẩn dữ liệu khỏi streaming.[2]

Node và edge

Node là hàm đọc state, làm việc rồi trả update. Edge là chuyển tiếp cố định hoặc có điều kiện, quyết định node nào chạy tiếp. Nói gọn: node làm việc, edge quyết định bước sau.[2]

  • START là điểm vào ảo đưa input vào graph; END đánh dấu đường kết thúc.[2]
  • Conditional edge: một hàm routing đọc state rồi trả về tên node, END, một danh sách node (fan-out) hoặc các Send.[2]
  • Cycle: edge quay lại node trước, ví dụ model ↔ tools như một agent ReAct. Vòng lặp phải có điều kiện dừng, thường là conditional edge dẫn tới END.[4]
  • Send: chạy cùng một node nhiều lần, mỗi lần một input riêng (map-reduce).[2]
  • Command: node vừa cập nhật state vừa chọn bước tiếp theo trong cùng một lần trả về.[2]

Graph phải được compile trước khi chạy. Bước compile kiểm cấu trúc (ví dụ node không nối với node nào) và là nơi gắn checkpointer.[2]

Mẹo thiết kế state: lưu dữ liệu thô trong state, đừng lưu prompt đã ghép sẵn; node nào cần thì tự ghép prompt. Như vậy nhiều node dùng chung dữ liệu theo cách riêng, đổi prompt không phải đổi schema, và khi gỡ lỗi bạn thấy đúng dữ liệu node nhận được.[18] Chọn gì đưa vào context của LLM là chủ đề của trang Context engineering.

Vòng lặp agent vẽ thành graph

Agent quen thuộc ở bài 1 thực chất là một graph hai node có vòng lặp: node model gọi LLM, node tools chạy tool; conditional edge sau model hỏi "còn tool call không?", có thì sang tools rồi quay lại model, không thì tới END.[4] create_agent chạy đúng vòng lặp này trên LangGraph.[21]

START → model ⇄ tools
          model → END   (khi hết tool call)

Runtime context

Có những thứ node cần nhưng không nên nằm trong state, như tên model hay kết nối database. Runtime context truyền chúng vào node lúc chạy mà không đưa vào state.[2] Với hệ thống nhiều khách hàng (tenant), đây là chỗ hợp lý để truyền mã tenant hoặc mã người dùng.

3.2 Super-step, chạy song song và giới hạn vòng lặp

Kích hoạt node

Node được kích hoạt khi nhận input qua một edge đi vào. Sau một super-step, node nào không còn message chờ thì nghỉ. Lần chạy kết thúc khi mọi node đều nghỉ.[2]

Song song và gộp nhánh

Hai node cùng được kích hoạt sẽ chạy song song trong cùng super-step; node gộp nhánh chạy sau khi cả hai xong.[4] Nếu hai nhánh cùng ghi một key mà key đó không có reducer, LangGraph báo lỗi INVALID_CONCURRENT_GRAPH_UPDATE.[30]

Recursion limit

Giới hạn số super-step trong một lần chạy; vượt quá thì có GraphRecursionError.[4] Từ bản 1.1.4, mặc định là 10.007 super-step.[2] create_agent của LangChain đặt 9.999.[20]

3.3 Persistence: checkpointer, thread và checkpoint

Checkpointer lưu gì, khi nào?

Checkpointer lưu một ảnh chụp state ở mỗi super-step, gom theo thread. thread_id là khóa chính để lưu và đọc checkpoint; muốn bắt đầu với state rỗng thì dùng thread_id mới.[7]

Mỗi checkpoint (một StateSnapshot) có: values (giá trị state), next (node sẽ chạy tiếp; rỗng là đã xong), config (gồm checkpoint_id), metadata (nguồn và số thứ tự super-step), parent_config (checkpoint trước) và tasks (kể cả interrupt đang chờ).[7]

Checkpoint phục vụ bốn việc: nối tiếp hội thoại, human-in-the-loop, time travel và chịu lỗi.[6]

Chọn checkpointer

  • InMemorySaver: giữ trong RAM, process khởi động lại là mất hết. Chỉ dùng để thử và test.[6]
  • langgraph-checkpoint-sqlite: hợp thử nghiệm và chạy ở máy.[7]
  • langgraph-checkpoint-postgres: tài liệu ghi là hợp production. Ngoài ra có bản cho MongoDB và Azure Cosmos DB.[7]

Durability mode quyết định lúc nào ghi xuống kho: "exit" chỉ ghi khi lần chạy thoát ra (xong, lỗi, hoặc dừng ở interrupt), nên process chết giữa chừng là mất; "async" ghi song song với bước sau (rủi ro nhỏ); "sync" ghi xong mới chạy bước sau (bền nhất, chậm hơn chút).[7] Trang Agent Server ghi mặc định là "async".[23]

State có thể được mã hóa khi lưu bằng EncryptedSerializer.[7] Liên quan tới dữ liệu cá nhân trong checkpoint, xem thêm trang Governance.

3.4 Durable execution và chịu lỗi

Chạy tiếp sau sự cố

Checkpoint được ghi ở ranh giới super-step, không ghi giữa một hàm. Vì vậy khi retry, cả node chạy lại từ đầu, bắt đầu từ state đã chốt gần nhất. Cơ chế chạy lại này giống nhau sau retry, sau interrupt và sau khi resume từ crash.[8]

Trong một super-step, node nào đã chạy xong thì kết quả được lưu thành "pending writes". Khi resume, các node đó không chạy lại.[7]

Khi một node lỗi, LangGraph có ba cơ chế ghép được với nhau: retry, timeout và error handler. RetryPolicy tự chạy lại node lỗi theo loại exception và thời gian chờ tăng dần; mặc định tối đa 3 lần chạy, tính cả lần đầu. Hết lượt retry thì error handler mới chạy.[8]

Khi tự host, process mới không tự chạy tiếp các thread dở dang: ứng dụng phải gọi lại graph.invoke(None, config) với cùng thread_id.[7] Agent Server có hàng đợi run và worker lấy run ra chạy.[23]

At-least-once: side effect phải idempotent

Cơ chế trên cho ngữ nghĩa at-least-once: một node có thể chạy hơn một lần. Nó không bảo đảm side effect bên ngoài (chuyển tiền, gửi email) chỉ xảy ra một lần. Code của bạn phải làm side effect idempotent.[8]

Cách làm tài liệu gợi ý: tạo idempotency key từ dữ liệu đã nằm trong state bền (ví dụ mã đơn), và dùng dịch vụ có tôn trọng key đó.[8] Node nhỏ thì checkpoint dày hơn và ít việc phải làm lại hơn.[18]

3.5 Human-in-the-loop: interrupt và resume

Cách hoạt động

Gọi interrupt(payload) ở bất kỳ đâu trong một node. Payload (dữ liệu JSON) được trả cho người gọi, nằm trong result["__interrupt__"].[9] Cần hai thứ: một checkpointer (production dùng loại bền) và một thread_id. Tài liệu gọi thread_id là "con trỏ bền" để biết resume từ đâu.[9]

def approval(state):
    d = interrupt({"cần duyệt": state["refund_amount"]})
    return {"approved": d["approved"]}
# Người duyệt xong, gọi lại với CÙNG thread_id:
graph.invoke(Command(resume={"approved": True}), config)

Giá trị trong Command(resume=…) trở thành giá trị trả về của lời gọi interrupt. Phải dùng đúng thread_id lúc dừng.[9]

Ba điều dễ sai

  1. Node chạy lại từ đầu khi resume. Mọi code đứng trước interrupt sẽ chạy lần nữa, nên đừng đặt việc không idempotent (như gọi API hoàn tiền) trước nó.[9]
  2. Không bọc try/except trần quanh interrupt. LangGraph dừng graph bằng cách ném một exception; bắt hết exception thì interrupt không về tới graph.[9]
  3. Thứ tự interrupt trong một node là quan trọng, vì giá trị resume được khớp theo vị trí.[9]

Mẫu thường gặp: duyệt hoặc từ chối trước một hành động quan trọng; cho người sửa state; đặt interrupt trong tool để mỗi lần gọi tool đều phải duyệt; kiểm tra input của người dùng.[9] interrupt_before/interrupt_after (static interrupt) chủ yếu để debug, không khuyên dùng cho human-in-the-loop.[9]

Với create_agent của LangChain, HumanInTheLoopMiddleware cho người duyệt, sửa hoặc từ chối tool call.[20]

3.6 Time travel: replay và fork

Replay: chạy lại từ một checkpoint cũ bằng cách gọi graph với config của checkpoint đó. Các node trước checkpoint không chạy lại vì kết quả đã lưu. Các node sau checkpoint chạy lại thật, kể cả lời gọi LLM, API và interrupt; replay không chỉ đọc cache.[10]

Fork: gọi update_state trên một checkpoint cũ để tạo checkpoint mới rẽ nhánh từ đó, rồi chạy tiếp. Fork không xóa gì; lịch sử cũ vẫn nguyên vẹn.[10] Replay từ checkpoint cuối (không còn node next) thì không làm gì.[10]

Xem lịch sử bằng get_state_history; checkpoint mới nhất đứng đầu danh sách.[7] LangSmith Studio cũng cho chạy lại một thread từ bất kỳ bước nào.[26]

3.8 Memory: ngắn hạn trong thread, dài hạn trong store

Short-term

Memory theo thread

Lịch sử hội thoại trong một phiên. LangGraph coi đây là một phần của state và lưu bằng checkpointer, nên thread resume được bất cứ lúc nào.[12] Hội thoại dài thì checkpoint tích lũy nhiều.[6]

Long-term

Memory xuyên thread (store)

Dữ liệu theo người dùng hoặc theo ứng dụng, dùng chung giữa các thread: sở thích, sự kiện, kiến thức chung.[6] Lưu thành tài liệu JSON trong store, xếp theo namespace (như thư mục, thường chứa user ID hoặc org ID) và key (như tên file).[12]

Các loại memory (semantic, episodic, procedural) và chiến lược ghi memory được giải thích kỹ ở trang Agent memory.

3.9 Subgraph và multi-agent

Subgraph

Subgraph là một graph được dùng như một node trong graph khác. Dùng để dựng multi-agent, tái sử dụng một cụm node, hoặc chia cho nhiều đội phát triển song song.[13]

  • Graph cha và subgraph chung key: thêm thẳng subgraph đã compile làm node.
  • Khác schema: gọi subgraph bên trong một node, tự chuyển state cha sang state con.
  • Subgraph mặc định kế thừa checkpointer của cha theo từng lần gọi. Interrupt ở subgraph nằm sâu mấy tầng vẫn lan lên graph ngoài cùng.[13]

Các mẫu multi-agent

  • Subagents: agent chính gọi các agent chuyên trách như gọi tool.
  • Handoffs: agent đang hoạt động đổi theo state, do tool call cập nhật.
  • Skills: một agent giữ quyền điều khiển, nạp thêm prompt và kiến thức chuyên môn khi cần.
  • Router: một bước phân loại input rồi chuyển cho một hoặc nhiều agent.
  • Custom workflow: tự dựng luồng bằng LangGraph, trộn logic cố định và agent.[14]

Gói langgraph-supervisor (mẫu supervisor) không còn được duy trì tích cực. Tài liệu khuyên chuyển sang mẫu subagents, và chỉ compile graph ngoài cùng với checkpointer.[15] Xem thêm trang Multi-agent và agentic RAG.

3.10 Hai cách viết: Graph API và Functional API

Cả hai đều tạo ra cùng một thứ: compile StateGraph hoặc tạo @entrypoint đều cho ra một đối tượng Pregel chạy trên cùng runtime.[5] Graph API khai báo node, edge và state chung một cách tường minh. Functional API bọc các hàm thường bằng @entrypoint và @task, dùng if/else và vòng lặp của Python, lưu kết quả các task vào checkpoint của entrypoint, và không có hình graph tĩnh.[16] Tài liệu khuyên dùng Graph API cho agent mới; Functional API hợp khi đã có sẵn code hoặc đang dùng framework khác.[16] Bảng so sánh ở mục 8.

3.11 Triển khai: tên sản phẩm hiện nay

Thư viện mã nguồn mở vẫn tên là LangGraph. Sản phẩm để host graph đã đổi tên nhiều lần:

  • LangGraph Platform: ra bản chính thức (GA) ngày 2025-05-14.[25]
  • Tháng 10/2025 đổi tên thành LangSmith Deployment.[25]
  • Tháng 11/2026 đổi tiếp thành LangSmith Agent Server.[24][22]

Agent Server là runtime cho agent, có durable execution, streaming theo thời gian thực và scale ngang.[22] Nó tổ chức công việc thành assistant (cấu hình), thread (state) và run (một lần chạy); run được đưa vào hàng đợi rồi worker lấy ra chạy; dữ liệu mặc định lưu trên PostgreSQL; có thêm store, cron job, webhook, và cách xử lý khi hai input tới cùng một thread lúc run trước chưa xong (double texting).[23] Khi chạy trên Agent Server, bạn không phải tự cấu hình checkpointer hay store.[6] Agent Server không bắt buộc graph viết bằng LangGraph.[23]

Khi phát triển ở máy, lệnh langgraph dev chạy một server local để LangSmith Studio (giao diện trực quan, miễn phí) kết nối, xem từng bước agent làm và các state trung gian.[26] Bạn cũng có thể tự host graph theo cách riêng; dùng Agent Server là một lựa chọn chứ không bắt buộc.

4. Ví dụ đi qua từng bước: agent hoàn tiền cần người duyệt

Tình huống: chuỗi bán lẻ điện máy Minh An (giả định) muốn agent xử lý yêu cầu hoàn tiền. Khoản hoàn trên 5.000.000 đ phải có trưởng nhóm chăm sóc khách hàng duyệt. Người duyệt thường trả lời sau vài giờ, có khi sáng hôm sau. Trong thời gian đó server có thể được deploy lại.

Tên công ty, số đơn, số tiền và ngưỡng duyệt là minh họa. Cơ chế từng bước theo tài liệu LangGraph. Cách chia node dựa trên hướng dẫn "Thinking in the Graph API", vốn dùng ví dụ agent email hỗ trợ khách hàng có chuyển cho người thật.[18]

5. Mô phỏng: chạy graph từng super-step

Tự bấm chạy graph hoàn tiền ở mục 4. Mỗi lần bấm Chạy super-step là một vòng Plan → Execution → Update → lưu checkpoint. Thử thêm: dừng chờ duyệt, làm sập process, đổi checkpointer, và bấm một checkpoint cũ để chạy lại từ đó (time travel).

Mô phỏng minh họa, chạy bằng JavaScript trong trình duyệt. Mô phỏng ghi checkpoint đồng bộ sau mỗi super-step (giống durability "sync"), và interrupt được gắn vào checkpoint hiện tại dưới dạng task đang chờ.[7] Số super-step, số checkpoint, số lượt chạy node và số lần gọi API đều do JS đếm thật trong lúc chạy. Khi replay, mô phỏng chỉ ghi các checkpoint của node chạy lại; bản thật có thể ghi thêm checkpoint, nên số checkpoint sau replay có thể chênh.

7. Bản đồ mối quan hệ

Nhóm đầu là ba cách viết, cả ba chạy trên cùng runtime Pregel. Runtime dùng checkpointer (theo thread) và store (xuyên thread). Hầu hết tính năng "cao cấp" như interrupt, time travel và durable execution đều đứng trên checkpointer. Hai ô màu cam là phần của LangSmith: host graph và quan sát graph.

10. Đánh giá và đo lường

Một graph đúng phải đúng ở hai lớp: lớp quyết định (LLM phân loại, chọn đường có đúng không) và lớp vận hành (dừng, lưu, chạy tiếp có đúng không). Các chỉ số dưới đây là gợi ý cho case hoàn tiền; cách chấm câu trả lời của LLM nói kỹ ở trang LLM evaluation.

Quyết định

Đi đúng đường

Với một bộ yêu cầu mẫu đã biết đáp án, đo tỷ lệ graph đi đúng nhánh: mọi khoản trên ngưỡng đều phải qua approval. Kiểm thêm tỷ lệ phân loại lý do đúng.

An toàn

Side effect trùng = 0

Đếm số lần hoàn tiền thật trên mỗi đơn sau các lần retry, resume và replay. Mục tiêu là đúng 1, vì node chạy theo at-least-once.[8]

Bền bỉ

Resume sau sự cố

Cố ý tắt process ở từng super-step rồi resume; so state cuối với lần chạy không lỗi. Checkpoint ở ranh giới super-step nên kết quả phải trùng.[8]

Con người

Interrupt

Tỷ lệ yêu cầu cần duyệt, thời gian chờ duyệt, tỷ lệ bị từ chối, và số interrupt bị "bỏ quên" (thread dừng quá lâu).

Chi phí

Số bước và độ trễ

Số super-step mỗi lần chạy (càng gần recursion limit càng đáng ngờ[4]), độ trễ và token theo từng node, xem trong trace. Chi phí token xem thêm trang LLM cost optimization.

Lưu trữ

Dung lượng checkpoint

Checkpoint tích lũy theo thời gian ở các hội thoại dài.[6] Theo dõi dung lượng và đặt chính sách dọn dẹp dữ liệu.

Test graph thế nào

  • Dùng pytest; tạo graph trong từng test và compile với một checkpointer mới.[29]
  • Test riêng một node qua graph.nodes (cách này bỏ qua checkpointer).[29]
  • Test một đoạn giữa graph: update_state với as_node là node đứng trước đoạn cần test, rồi chạy với interrupt_after ở node muốn dừng. InMemorySaver là đủ cho test.[29]

Câu hỏi tự kiểm tra

1. Super-step là gì? Hai node chạy song song nằm ở mấy super-step?

Super-step là một "nhịp" của graph: chọn các node được kích hoạt, chạy chúng song song, rồi ghi update vào state. Hai node song song nằm chung một super-step; node nối tiếp nằm ở các super-step khác nhau.[2][5]

2. Vì sao interrupt cần checkpointer và thread_id?

Khi dừng, graph có thể chờ hàng giờ và process có thể không còn. State phải được lưu ở đâu đó (checkpointer), và lúc resume phải biết lấy lại state nào (thread_id, "con trỏ bền").[9]

3. Khi resume, code đứng trước interrupt() có chạy lại không? Hệ quả là gì?

Có. Cả node chạy lại từ đầu, nên mọi việc trước interrupt chạy lần hai. Việc không idempotent (chuyển tiền, gửi email) không được đặt ở đó.[9]

4. Hai node song song cùng ghi key notes mà không có reducer thì sao?

LangGraph báo lỗi INVALID_CONCURRENT_GRAPH_UPDATE vì không biết gộp thế nào. Khai báo reducer, ví dụ operator.add, để nối hai update.[30]

5. Memory trong thread khác memory trong store thế nào?

Memory ngắn hạn là một phần state của một thread, lưu bằng checkpointer. Memory dài hạn nằm trong store, xếp theo namespace và key, đọc được từ mọi thread.[12]

6. Replay từ một checkpoint cũ có đọc lại kết quả LLM đã lưu không?

Chỉ với các node trước checkpoint. Các node sau checkpoint chạy lại thật, kể cả lời gọi LLM, API và interrupt.[10]

7. create_agent của LangChain liên quan gì tới LangGraph?

create_agent dùng LangGraph bên dưới để chạy vòng lặp agent, nên agent đó có sẵn persistence, human-in-the-loop và durable execution của LangGraph.[19][21]

8. Khi nào chọn Functional API thay vì Graph API?

Khi đã có code sẵn hoặc đang dùng framework khác và muốn thêm checkpoint, interrupt mà không viết lại thành graph. Với agent mới, tài liệu khuyên Graph API.[16]

9. Sản phẩm host graph hiện tên là gì? Có bắt buộc dùng không?

LangSmith Agent Server (trước đó là LangSmith Deployment, và trước nữa là LangGraph Platform).[22][25] Không bắt buộc: LangGraph là thư viện MIT, bạn có thể tự host.[28]
