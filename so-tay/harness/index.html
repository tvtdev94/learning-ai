Hiểu Agent Harness từ gốc

Một LLM tự nó chỉ làm được một việc: nhận văn bản vào và sinh văn bản ra. Để nó đọc file, chạy lệnh, sửa code qua nhiều bước một cách an toàn, cần cả một lớp phần mềm bao quanh: gọi model, chạy tool, ghép context, kiểm quyền, biết khi nào dừng. Lớp phần mềm đó gọi là agent harness (còn gọi là scaffold): hệ thống giúp model hoạt động như một agent, xử lý đầu vào, điều phối các lần gọi tool và trả kết quả.[24]

Cách nhớ gọn: agent = model + harness. Model là phần "suy nghĩ" (được huấn luyện sẵn, gọi qua API). Harness là mọi thứ còn lại do con người viết bằng code và cấu hình. Anthropic mô tả agent về cơ bản là "LLM dùng tool dựa trên phản hồi từ môi trường, trong một vòng lặp"[1], và gọi bộ Claude Agent SDK của họ là một "agent harness" đa dụng[2]. Danh sách thành phần chi tiết trên trang này là phần tổng hợp từ nhiều nguồn ở cuối trang. Trang AI Agent nói về agent nói chung; trang này đi sâu vào phần "khung" bên trong.

Vì sao gọi là "harness"?

🐎 Ngựa và bộ yên cương

"Harness" nghĩa gốc là bộ yên cương, dây đai để khai thác sức của con ngựa. Ngựa khỏe (model) mà không có yên cương thì không kéo được xe, cũng không ai điều khiển được.

Harness biến sức mạnh thô của model thành công việc có hướng, có giới hạn.

🚗 Động cơ và chiếc xe

Model giống động cơ. Harness giống phần còn lại của xe: vô lăng (vòng lặp điều khiển), bánh xe (tool), phanh (quyền, giới hạn), bình xăng (ngân sách context), đồng hồ (log).

Cùng một động cơ lắp vào hai chiếc xe khác nhau thì chạy rất khác nhau. Tương tự, nghiên cứu SWE-agent cho thấy chỉ riêng cách thiết kế giao diện giữa agent và máy tính đã ảnh hưởng tới hành vi và hiệu quả của agent.[10]

Vì sao cần harness?

Lý do 1

Model không tự hành động

Khi model "gọi tool", nó chỉ viết ra một yêu cầu có cấu trúc (tên tool + tham số). Code của ứng dụng mới là bên thực sự chạy, rồi gửi kết quả lại cho model.[5][6]

Ngoại lệ: một số tool do chính nhà cung cấp chạy sẵn trên server của họ (ví dụ tìm kiếm web).[5]

Lý do 2

Model không nhớ giữa các lần gọi

Với cách dùng API phổ biến, mỗi lần gọi là độc lập (stateless): ứng dụng phải gửi lại toàn bộ lịch sử hội thoại.[7] Harness giữ lịch sử và quyết định gửi lại những gì.

Một số API có thêm tùy chọn để server giữ hội thoại giúp bạn, nhưng việc chọn đưa gì vào context vẫn là việc của harness.

Lý do 3

Model có thể sai hoặc làm liều

Model có thể chọn lệnh nguy hiểm, hoặc làm theo chỉ dẫn độc hại nằm trong file, trang web (prompt injection).[19] Harness đặt quyền, sandbox, giới hạn và hỏi người dùng khi cần.[16]

Lý do 4

Context có giới hạn

Model chỉ đọc được một lượng token giới hạn mỗi lần (context window). Context càng dài, model nhớ lại thông tin càng kém chính xác[3]; một nghiên cứu năm 2023 còn thấy thông tin nằm ở giữa context dài bị dùng kém nhất.[11] Harness chọn đưa gì vào, cắt gì, tóm tắt gì.

Ví dụ quen thuộc: các coding agent dạng CLI hoặc tích hợp IDE là harness bao quanh một model. Phần bạn cài đặt và tương tác (giao diện, quyền, file hướng dẫn, lịch sử) là harness; model được gọi qua API. Ví dụ, tài liệu công khai của Claude Code mô tả các thành phần kiểu harness như luật quyền[16], hooks[17] và file hướng dẫn dự án[15]. Trang này mô tả cấu trúc chung, không mô tả nội bộ của sản phẩm cụ thể nào.

Từ "harness" còn một nghĩa khác: evaluation harness, khung chạy bộ bài kiểm tra để chấm điểm model hoặc agent. Nghĩa này được giải thích ở mục 8.

2. Flow hoạt động: vòng lặp agent

Trái tim của harness là một vòng lặp: ghép context → gọi model → đọc output. Nếu model yêu cầu gọi tool (một hoặc nhiều tool trong cùng một lượt), harness kiểm quyền, chạy tool, đưa kết quả vào lịch sử rồi lặp lại. Khi model trả lời mà không yêu cầu tool nào nữa (hoặc chạm một giới hạn), vòng lặp dừng.[5]

Ý tưởng để model xen kẽ "suy nghĩ" và "hành động" với môi trường bên ngoài, rồi dùng kết quả hành động để suy nghĩ tiếp, được trình bày sớm trong nghiên cứu ReAct.[9]

Ba điều cần nhớ về vòng lặp

Model

Chỉ quyết định, không làm

Mỗi lượt, model đọc context rồi trả về văn bản hoặc tool call. Nó không tự chạy lệnh, không tự đọc file.[5]

Harness

Làm và ghi lại

Harness thực thi tool call, rồi đưa kết quả (kể cả lỗi) vào lịch sử để lượt sau model "thấy" chuyện gì đã xảy ra.[6]

Dừng

Phải có điểm dừng rõ ràng

Thường là khi model trả lời không kèm tool call. Ngoài ra nên có điều kiện dừng như số vòng lặp tối đa để giữ quyền kiểm soát.[1]

Liên hệ với RAG: trong RAG, hệ thống tìm tài liệu một lần rồi đưa vào prompt. Trong agent, việc tìm kiếm có thể là một tool mà model tự quyết định gọi, gọi nhiều lần (đây chính là agentic RAG).

3. Ví dụ đi qua từng bước

Một lập trình viên nhờ coding agent sửa test đang fail. Bấm từng bước để xem harness làm gì và model thực sự nhìn thấy gì (khung "Context" bên dưới mỗi bước). Tên tool, nội dung file, số lượt, token và phần trăm context đều là minh họa, không lấy từ sản phẩm cụ thể nào.

4. Từ điển khái niệm

Mỗi thẻ có định nghĩa ngắn, ví dụ, và liên kết sang khái niệm liên quan. Lọc theo nhóm hoặc gõ để tìm (gõ không dấu cũng được).

5. Bản đồ mối quan hệ

Vòng lặp agent là "trạm điều phối" ở giữa: nó lấy context đã ghép gửi cho model, nhận lại tool call, đưa qua kiểm quyền, cho chạy tool, rồi cập nhật context. Các thành phần khác cắm vào trạm này.

Quan hệ "phụ thuộc" quan trọng nhất

  • Context quyết định model biết gì: thông tin không được ghép vào thì với model coi như không tồn tại.
  • Mô tả tool quyết định model dùng tool có đúng không: mô tả mơ hồ hoặc nhiều tool trùng chức năng thì model dễ chọn nhầm.[4]
  • Kết quả tool quyết định model sửa sai được không: thông báo lỗi rõ ràng, có hướng sửa thì model tự điều chỉnh được; mã lỗi khó hiểu thì model đoán mò.[4]
  • Quyền và sandbox quyết định sai lầm của model gây hại tới đâu.

Model không thấy phần lớn harness

  • Luật quyền, sandbox, hooks, retry, log chạy bên ngoài model. Model chỉ biết về chúng nếu được mô tả trong context hoặc khi nhận kết quả (ví dụ "bị chặn").
  • Vì vậy khi một hành động bị chặn, harness nên báo lại lý do như một kết quả tool để model đổi hướng, thay vì im lặng.
  • Ngược lại, lời dặn và file hướng dẫn chỉ là context, không phải luật cưỡng chế. Muốn chắc chắn chặn một hành động thì phải dùng quyền hoặc hook ở phía harness.[15]

Quy tắc dễ nhớ: đổi model là đổi "bộ não"; đổi harness là đổi "những gì bộ não được thấy, được làm và được phép làm". Khi agent làm kém, hãy kiểm tra harness (context, tool, luật) trước khi kết luận model kém. Anthropic kể rằng khi làm agent cho SWE-bench, họ dành nhiều thời gian tối ưu tool hơn cả prompt tổng thể.[1]

7. Lỗi thường gặp và cách chẩn đoán

Khi agent làm sai, đừng vội kết luận "model kém". Việc đầu tiên là mở transcript (còn gọi là trace hay trajectory: bản ghi đầy đủ một lần chạy, gồm cả tool call và kết quả tool)[24] và xem model đã thực sự nhận được gì, đã yêu cầu gì, harness đã làm gì.[4] Đi theo thứ tự dưới đây.

Cây chẩn đoán

  1. Model có nhận đủ thông tin không?
    Không → lỗi ghép context: file hướng dẫn không được nạp, yêu cầu gốc bị tóm tắt mất, kết quả tool bị cắt đúng phần quan trọng.
  2. Tool có được mô tả rõ, và trả kết quả rõ không?
    Không → lỗi thiết kế tool: mô tả mơ hồ, tham số khó hiểu, thông báo lỗi trống trơn kiểu "failed".
  3. Harness có làm đúng điều model yêu cầu không?
    Không → bug harness: đọc sai tham số, timeout quá ngắn, bị chặn mà không báo lại cho model.
  4. Thông tin đủ, tool tốt, harness đúng mà model vẫn chọn sai?
    Có → giới hạn của model hoặc lời dặn chưa rõ: sửa system prompt, chia nhỏ nhiệm vụ, thêm bước kiểm chứng, hoặc thử model mạnh hơn.

Phiên chết giữa chừngLỗi tạm thời (quá tải, rate limit) mà không có retry; không lưu trạng thái để chạy tiếp.[20]
Cùng yêu cầu, lúc tốt lúc tệOutput của model được lấy mẫu nên có thể khác nhau giữa các lần chạy; một lần chạy không đủ để kết luận.[23]
Prompt injection đáng sợ hơn với agent: lời dặn của bạn và dữ liệu từ bên ngoài cùng nằm trong một context, nên model có thể nhầm dữ liệu thành lệnh. Chatbot thường chỉ nói sai; agent có tool thì có thể làm sai (xóa file, gửi dữ liệu ra ngoài). OWASP nhận định chưa rõ có cách phòng chống tuyệt đối nào, và khuyên giới hạn quyền ở mức tối thiểu, có người duyệt cho thao tác đặc quyền.[19] Sandbox vẫn giữ giới hạn ngay cả khi injection qua mặt được quyết định của model.[16][18]

8. Đánh giá: evaluation harness và đánh giá harness

Hai nghĩa, đừng nhầm: agent harness là khung để model làm việc. Evaluation harness là hạ tầng chạy việc đánh giá từ đầu đến cuối: chạy các task, ghi lại mọi bước, chấm điểm và tổng hợp kết quả.[24] Ví dụ: dự án mã nguồn mở lm-evaluation-harness của EleutherAI là "khung thống nhất" để chấm model ngôn ngữ trên rất nhiều tác vụ đánh giá[21]; benchmark SWE-bench có evaluation harness chạy trong container Docker để kết quả lặp lại được.[22]

Một evaluation harness gồm những gì?

1Bộ task

Danh sách việc cần làm, mỗi việc có cách xác định đúng/sai.

2Môi trường sạch

Mỗi task chạy trong trạng thái ban đầu giống nhau (ví dụ container), không bị lần chạy trước ảnh hưởng.[22]

3Chạy agent

Mỗi lần thử một task gọi là một trial; ghi lại toàn bộ transcript.[24]

4Grader

Chấm kết quả: chạy test tự động, so đáp án, hoặc dùng LLM-as-judge.

5Báo cáo

Tỷ lệ thành công, chi phí, thời gian; so với lần trước.

Đánh giá một agent harness tốt hay dở

Cách làm

Giữ model cố định, đổi harness

  • Chạy cùng model trên cùng bộ task với harness cũ và mới. Đổi một thứ mỗi lần (lời dặn, một tool, cách compaction) để biết cái gì thật sự giúp.
  • Task nên lấy cảm hứng từ việc thật, dữ liệu thật, không quá đơn giản.[4]
  • Chạy mỗi task nhiều trial, vì output của model thay đổi giữa các lần chạy.[24]
  • Đọc transcript thô (gồm tool call và kết quả tool) của các task thất bại, đừng chỉ nhìn con số tổng.[4]
  • Giữ một bộ task cũ làm regression: sửa chỗ này không được làm hỏng chỗ khác.
Đo gì

Không chỉ "làm xong hay không"

  • Tỷ lệ hoàn thành task, kiểm bằng grader khách quan khi có thể (ví dụ test tự động).
  • Chi phí: token, số lượt, thời gian.
  • An toàn: số hành động bị chặn, số vi phạm luật.
  • Sự can thiệp: người dùng phải duyệt hoặc sửa bao nhiêu lần.
  • pass@k: một bài được tính là giải được nếu ít nhất một trong k lần thử qua được test[23]. Hợp khi chỉ cần thành công một lần.
  • pass^k: xác suất cả k lần thử đều thành công. Hợp khi người dùng cần agent ổn định mọi lần. Ví dụ của nguồn: thành công 75% mỗi lần thì cả 3 lần đều đạt chỉ khoảng 42% (0,75³ ≈ 0,42).[24]
Đọc kết quả: nếu đổi harness mà tỷ lệ thành công tăng trong khi model giữ nguyên (cùng phiên bản, cùng cấu hình), và mức tăng lớn hơn dao động giữa các lần chạy, thì có thể quy phần tăng đó cho harness. Khi đánh giá agent, thứ được đo là harness và model làm việc cùng nhau.[24] Đây là lý do khi so sánh hai agent, cần biết cả model và harness, chỉ biết tên model là chưa đủ.

Tự kiểm tra: trả lời được là đã nắm cốt lõi

1. Model và harness khác nhau thế nào? Nêu một việc chỉ harness làm được.

Model là mạng nơ-ron đã huấn luyện, chỉ nhận context và sinh text hoặc tool call. Harness là phần mềm bao quanh: ghép context, chạy tool, kiểm quyền, giữ lịch sử, quyết định dừng, ghi log. Ví dụ việc chỉ harness làm được: thực sự chạy một lệnh trên máy, hoặc chặn một lệnh nguy hiểm.

2. Khi model "gọi tool", ai thực sự chạy tool? Model thấy gì sau đó?

Harness chạy. Model chỉ viết ra yêu cầu có cấu trúc (tên tool + tham số). Sau khi chạy, harness đưa kết quả (hoặc lỗi, hoặc "bị chặn") vào lịch sử, và ở lượt sau model đọc thấy kết quả đó trong context.

3. Vì sao harness phải gửi lại lịch sử mỗi lượt, và điều đó gây ra vấn đề gì?

Vì với cách dùng API phổ biến, model không nhớ gì giữa các lần gọi. Hệ quả: context lớn dần theo số lượt, tốn token và có lúc chạm giới hạn context window. Harness xử lý bằng cách cắt output dài, tóm tắt (compaction), và một số nhà cung cấp có prompt caching để giảm chi phí phần lặp lại.

4. Vòng lặp agent dừng khi nào? Nêu ít nhất ba điều kiện.

Khi model trả lời mà không còn tool call; khi chạm giới hạn số lượt; khi hết ngân sách token, tiền hoặc thời gian; khi người dùng bấm dừng; khi gặp lỗi không phục hồi được. Lưu ý: model cũng có thể dừng vì output bị cắt hoặc vì từ chối; đó không phải là xong việc.

5. Compaction giúp gì và có rủi ro gì?

Giúp phiên làm việc dài không bị tràn context bằng cách tóm tắt các lượt cũ. Rủi ro: bản tóm tắt bỏ sót chi tiết quan trọng (ràng buộc, quyết định), khiến agent "quên" và làm sai về sau.

6. Agent làm sai, bạn kiểm tra theo thứ tự nào?

Mở trace. (1) Model có nhận đủ thông tin không? (2) Tool có mô tả và kết quả rõ không? (3) Harness có làm đúng điều model yêu cầu không? (4) Nếu ba điều trên đều ổn mà vẫn sai, lúc đó mới xét lời dặn hoặc model.

7. "Evaluation harness" khác "agent harness" thế nào?

Agent harness (scaffold) giúp model làm việc. Evaluation harness là hạ tầng chạy cả agent qua một bộ task trong môi trường kiểm soát, ghi lại transcript và chấm điểm. Một bên để làm, một bên để đo.

8. Làm sao biết harness mới tốt hơn harness cũ?

Giữ nguyên model, chạy cả hai harness trên cùng bộ task, mỗi task nhiều lần. So tỷ lệ thành công, chi phí, số lượt, số lần người dùng phải can thiệp, và đọc transcript các lần thất bại.

9. Vì sao ghi một quy tắc vào file hướng dẫn chưa đủ để chặn một hành động? Dùng gì thay thế?

Vì file hướng dẫn chỉ được nạp vào context như lời dặn; model có thể bỏ qua, hoặc bị prompt injection lôi đi. Muốn chặn chắc chắn phải dùng cơ chế phía harness: luật quyền (chặn hoặc hỏi), hook kiểm tra trước khi chạy tool, và sandbox giới hạn file, mạng.
