10 mẹo dùng Claude Code hằng ngày10 everyday Claude Code tips

Mười mẹo dưới đây lấy từ tài liệu chính thức của Claude Code. Lệnh, cờ và phím tắt đều đã đối chiếu lại ngày 20/11/2026. Claude Code ra bản mới thường xuyên, nên nếu lệnh nào chạy khác đi, hãy xem lại tài liệu ở mục Nguồn.

Nói cho Claude điều nó không tự thấyTell Claude what it can't see

Claude bắt đầu mỗi việc bằng cách đọc code, nên cấu trúc thư mục, quy ước đặt tên hay framework test thì nó tự tìm ra. Thứ nó không thấy là những gì chưa từng nằm trong repo: một quyết định chốt trong buổi họp, quy trình deploy chỉ một người nhớ, biến môi trường mà bộ test tích hợp cần.[1]

Claude starts every task by reading your code, so it finds your folder layout, naming conventions and test framework on its own. What it can't see is anything that was never in the repo: a decision made in a meeting, a deploy process one person remembers, the environment variable your integration tests need.[1]

Prompt cũng vậy. Nêu tên file, tả triệu chứng, nói rõ thế nào là xong thì bạn đỡ được một vòng sửa qua lại. Ví dụ dưới đây phỏng theo tài liệu:

The same goes for a prompt. Name the file, describe the symptom and say what "fixed" looks like, and you skip a round of corrections. This example is adapted from the docs:

Thay vìInstead ofHãy viếtTry
Thay vìInstead of"sửa lỗi đăng nhập""fix the login bug" Hãy viếtTry"người dùng báo đăng nhập lỗi sau khi phiên hết hạn. xem phần refresh token trong src/auth/, viết một test fail tái hiện lỗi, rồi sửa""users report login fails after the session times out. look at token refresh in src/auth/, write a failing test that reproduces it, then fix it"

Có sẵn thứ Claude cần thì đưa luôn, đừng tả lại: gõ @ kèm đường dẫn để gửi nội dung file, dán ảnh chụp màn hình lỗi, hoặc chuyển output từ shell vào:[1]

If you already have what Claude needs, hand it over instead of describing it: type @ and a path to include a file, paste a screenshot of the error, or pipe output in from your shell:[1]

$ cat error.log | claude -p "what's going on here"

Khi chưa rõ mình muốn gì, nhờ Claude phỏng vấn bạn cho tới khi đủ ý để viết spec vào SPEC.md. Sau đó mở một phiên mới để làm theo spec, phiên đó bắt đầu với context sạch và tiêu chí "xong" đã ghi thành văn bản.[1]

When you don't know exactly what you want yet, ask Claude to interview you until it can write the spec to SPEC.md. Then start a fresh session to build from it, with a clean context and a written definition of done.[1]

Bật plan mode trước khi sửa nhiềuUse plan mode before a big change

Ở plan mode, Claude đọc file, chạy lệnh để tìm hiểu rồi viết kế hoạch, nhưng không sửa source cho tới khi bạn duyệt kế hoạch đó.[2] Bạn đọc kế hoạch, sửa chỗ hiểu sai, rồi mới để Claude làm. Ngoại lệ: trong phiên terminal có sẵn chế độ bypass permissions, ví dụ phiên mở bằng --dangerously-skip-permissions hoặc --allow-dangerously-skip-permissions, plan mode không chặn nữa. Claude vẫn được dặn chỉ lên kế hoạch, nhưng lệnh sửa file hay lệnh shell nó thử chạy sẽ chạy luôn mà không hỏi.[2]

In plan mode Claude reads files, runs shell commands to explore and writes a plan, but it doesn't edit your source until you approve that plan.[2] You read the plan, fix what it got wrong, and only then let Claude build. The exception: in an interactive terminal session where bypass permissions is available, for example one started with --dangerously-skip-permissions or --allow-dangerously-skip-permissions, plan mode stops blocking. Claude is still told to plan without editing, but a file edit or shell command it attempts runs without a prompt.[2]

  • Nhấn Shift+Tab để đổi chế độ quyền. Từ auto, lần nhấn đầu chuyển sang default (Manual), sau đó lần lượt là acceptEdits rồi plan.
  • Chỉ cần plan cho một prompt thì gõ /plan ở đầu prompt đó.
  • Mở phiên ở plan mode ngay từ đầu: claude --permission-mode plan.
  • Muốn thoát thì nhấn Shift+Tab lần nữa. Riêng ở màn hình duyệt kế hoạch, nhấn Esc trước, vì Shift+Tab ở đó là duyệt luôn kế hoạch.[2]
  • Press Shift+Tab to cycle permission modes. From auto, the first press switches to default (Manual), then acceptEdits, then plan.
  • For a single prompt, start it with /plan.
  • To start the whole session in plan mode: claude --permission-mode plan.
  • Press Shift+Tab again to leave. At the plan approval prompt, press Esc first, because Shift+Tab there approves the plan.[2]

Từ Claude Code v2.1.283, phiên tương tác mới trong terminal và VS Code mặc định chạy ở auto mode.[2]

Since Claude Code v2.1.283, new interactive terminal and VS Code sessions start in auto mode.[2]

3

Giữ CLAUDE.md thật ngắnKeep CLAUDE.md short

Claude Code nạp CLAUDE.md vào mọi phiên, nên mỗi dòng trong đó chiếm một phần chú ý của Claude trong mọi việc, kể cả việc không liên quan. Tài liệu khuyên chỉ ghi:[1]

Claude Code loads CLAUDE.md into every session, so every line takes a little of Claude's attention on every task, relevant or not. The docs suggest keeping only:[1]

  • lệnh kiểm tra của repo: test, typecheck, lint, và cách chạy riêng một file test;
  • chỗ code dễ gây hiểu lầm, ví dụ một pattern cũ còn khắp nơi nhưng code mới không được chép theo;
  • quyết định không có trong repo, như cách deploy hay helper xử lý lỗi mà nhóm đã chọn;
  • điều bạn đã phải nhắc Claude hai lần.
  • how to check work in this repo: the test, typecheck and lint commands, and how to run one test file;
  • places where the code is misleading, like an old pattern that's everywhere but new code must not copy;
  • decisions that aren't in the repo, like how deploys work or which error helper the team chose;
  • anything you've had to correct twice.

/init tạo bản đầu từ codebase, phần việc còn lại chủ yếu là xóa bớt; nên giữ dưới 200 dòng. Chạy /context all để chắc Claude đã nạp file. Sở thích riêng của bạn để trong CLAUDE.local.md và thêm file này vào .gitignore. Luật chỉ dành cho một phần code thì đặt trong .claude/rules/ kèm bộ lọc paths:, để nó chỉ nạp khi Claude làm ở phần đó.[1]

Muốn biết nên cắt gì, chạy /doctor: nó gợi ý bỏ những dòng Claude tự suy ra được từ code. /doctor prompt-audit chỉ ra chỉ dẫn viết cho model đời cũ, chỉ dẫn trỏ tới file không còn, và chỉ dẫn mâu thuẫn nhau.[1]

To find what to cut, run /doctor: it suggests cuts for anything Claude can already work out from the code. /doctor prompt-audit flags instructions written for older models, ones that point at files that no longer exist, and ones that contradict each other.[1]

/init generates a first version from your codebase, and most of the work after that is deleting lines; stay under 200. Run /context all to confirm Claude loaded the file. Personal preferences go in CLAUDE.local.md, added to .gitignore. A rule for one part of the codebase goes in .claude/rules/ with a paths: filter, so it only loads when Claude works there.[1]

Muốn có luật chung cho mọi dự án, xem bài 1 về CLAUDE.md global.

For one set of rules across all your projects, see post 1 on the global CLAUDE.md.

4

Cho Claude một phép kiểm tra để tự chạyGive Claude a check it can run

Claude dừng khi thấy việc trông có vẻ xong. Không có gì để chạy thì "trông có vẻ xong" là tất cả những gì nó có, và bạn thành bộ test.[1] Có một phép kiểm trả về đạt hoặc không đạt thì Claude tự sửa, tự chạy lại cho tới khi đạt. Phép kiểm có thể là file test, exit code của bản build, linter, hay một script so output với fixture. Nếu repo đã có, dòng hữu ích nhất trong CLAUDE.md chính là lệnh chạy nó.[1]

Claude stops when the work looks done. With nothing to run, "looks done" is all it has, and you become the test suite.[1] Give it a check that comes back pass or fail and it fixes and reruns until the check passes. That can be a test file, a build's exit code, a linter, or a script that diffs output against a fixture. If your repo has one, the most useful line in CLAUDE.md is the command that runs it.[1]

Xin bằng chứng: lệnh Claude đã chạy và output của nó. Một câu "all tests pass" không nói được bao nhiêu. Muốn có một lượt soát độc lập, /code-review review diff bằng một subagent mới, chưa từng thấy hội thoại của bạn.[1]

Claude báo xong rồi thì chạy thêm /verify: Claude build, chạy app và tự xem kết quả, bắt được loại lỗi mà test và typecheck bỏ sót. Muốn Claude không dừng trước khi đạt một điều kiện, dùng /goal, ví dụ /goal all tests in tests/auth pass and lint is clean: sau mỗi lượt, một model riêng kiểm điều kiện đó và Claude làm tiếp cho tới khi đạt.[1]

Once Claude says it's done, run /verify: Claude builds and runs the app and looks at the result, which catches the kind of problem tests and typechecks miss. To keep Claude going until a condition holds, use /goal, like /goal all tests in tests/auth pass and lint is clean: a separate model checks the condition after every turn, and Claude keeps going until it's met.[1]

Ask for evidence: the command Claude ran and its output. "All tests pass" on its own tells you very little. For a second pair of eyes, /code-review reviews the diff in a fresh subagent that never saw your conversation.[1]

Luật không có ngoại lệ thì dùng hook hoặc denyRules with no exceptions go in hooks or deny rules

CLAUDE.md, prompt và skill là chỉ dẫn để Claude cân nhắc: gần như lần nào nó cũng làm theo, nhưng không có gì bảo đảm. Hook, deny rule và managed setting thì do Claude Code thực thi, lần nào cũng chạy, bất kể model nghĩ gì.[1] Nếu bạn cứ thêm chữ IMPORTANT vào một dòng mà Claude vẫn bỏ qua, dòng đó nên chuyển thành hook.

CLAUDE.md, prompts and skills are instructions Claude weighs: it follows them nearly every time, with no guarantee. Hooks, deny rules and managed settings are applied by Claude Code itself, every time, whatever the model decides.[1] If you keep adding IMPORTANT to a line and Claude still misses it, that line belongs in a hook.

Chặn đọc .env bằng deny rule trong .claude/settings.json. Deny rule có hiệu lực ở mọi chế độ quyền, kể cả auto và bypassPermissions:[1]

Block reading .env with a deny rule in .claude/settings.json. Deny rules hold in every permission mode, auto and bypassPermissions included:[1]

.claude/settings.json
{
  "permissions": {
    "deny": ["Read(./.env)", "Read(./.env.local)", "Read(./secrets/**)"]
  }
}

Rule Read chặn cả các lệnh đọc file quen thuộc như cat .env, nhưng không chặn một script tự mở file. Việc liên quan tới bảo mật thì nên dùng cả deny rule lẫn sandbox (bật bằng /sandbox).[1]

The Read rule also catches common file-reading commands like cat .env, but not a script that opens the file. For anything security-related, use both deny rules and the sandbox (turn it on with /sandbox).[1]

Bắt typecheck phải qua mới được kết thúc lượt bằng hook Stop. Hook này cũng đặt trong .claude/settings.json. Script thoát với mã 2 thì Claude phải quay lại làm tiếp, và những gì in ra stderr là lý do Claude nhận được:[1]

Require a passing typecheck before the turn ends with a Stop hook. It also goes in .claude/settings.json. Exit code 2 sends Claude back to work, and whatever goes to stderr is the reason it gets:[1]

.claude/settings.json
{
  "hooks": {
    "Stop": [
      { "hooks": [ { "type": "command", "command": "pnpm tsc --noEmit 1>&2 || exit 2" } ] }
    ]
  }
}

Hook không chặn mãi: nếu nó chặn tám lần liên tiếp mà giữa chừng không có tool call nào, Claude Code bỏ qua lần chặn kế tiếp và kết thúc lượt.[1]

The hook can't block forever: if it blocks eight stops in a row with no tool call between them, Claude Code overrides the next block and ends the turn.[1]

Đừng lạm dụng. Hook dành cho luật không có ngoại lệ nào; cái gì chỉ là sở thích thì để Claude tự cân nhắc.[1]

Don't overdo it. A hook is for a rule with zero exceptions; anything that's only a preference can stay Claude's call.[1]

Dừng sớm, quay lại khi cầnStop early, rewind when needed

Xem phút đầu tiên Claude làm. Thấy nó đi lệch thì nhấn Esc: Claude dừng ngay và giữ lại phần đã làm, bạn chỉ hướng lại mà không mất gì.[1]

Watch the first minute. The moment Claude drifts, press Esc: it stops and keeps the work so far, so you can redirect without losing anything.[1]

Nhấn Esc hai lần khi ô nhập đang trống, hoặc gõ /rewind, để mở menu quay lại. Ở đó bạn đưa code, hội thoại, hoặc cả hai về thời điểm của một prompt trước đó.[1][3] Nhờ vậy cứ thử cách táo bạo trước, không ổn thì quay lại. Lưu ý: checkpoint chỉ theo dõi file Claude sửa bằng công cụ sửa file của nó. File chỉ bị đổi qua lệnh Bash, và file do subagent sửa mà Claude chưa từng sửa trong hội thoại, thì không được khôi phục, nên vẫn cần git.[1][4]

Press Esc twice on an empty prompt, or type /rewind, to open the rewind menu, where you roll the code, the conversation or both back to an earlier prompt.[1][3] That makes it cheap to try the bolder approach first. Checkpoints only cover files Claude edited with its own file tools; a file changed only by a Bash command, or edited by a subagent but never by Claude in your conversation, isn't restored, so keep using git.[1][4]

Đã sửa cùng một chỗ hai lần mà vẫn sai thì đừng sửa lần thứ ba. Chạy /clear rồi viết một prompt mới gộp những gì bạn vừa rút ra; hội thoại cũ đang chứa hai lần thử hỏng mà Claude cứ phải đọc lại.[1]

If you've corrected the same thing twice and it's still wrong, skip the third correction. Run /clear and write one new prompt that folds in what you learned; the old conversation holds two failed attempts that Claude keeps re-reading.[1]

Giữ context gọn để tốn ít hơnKeep context lean to spend less

Mỗi request gửi lại cả hội thoại, nên một phiên đã gom ba việc không liên quan sẽ đọc lại cả ba ở mỗi lượt của việc thứ tư.[1]

Every request sends the whole conversation, so a session that has collected three unrelated tasks re-reads all three on every turn of the fourth.[1]

  • /clear giữa hai việc không liên quan. /clear oauth-migration đặt tên cho phiên vừa rời để sau này quay lại. Việc kéo dài nhiều ngày thì gõ /rename oauth-migration trong phiên, hôm sau mở lại bằng claude --resume oauth-migration, kèm cả checkpoint; claude --continue mở lại phiên gần nhất.[1]
  • /compact kèm trọng tâm, ví dụ /compact keep the API changes and the test commands. Trên phiên dài, bản thân lệnh này cũng là một request lớn.[1]
  • /btw hỏi nhanh một câu mà không thêm gì vào lịch sử hội thoại.[3]
  • /usage cho biết mức dùng của bạn tiêu vào đâu. Trên gói Pro, Max, Ultra, Team và Enterprise, nó chia theo skill, subagent, plugin và MCP server.[1]
  • MCP server đang kết nối luôn thêm tên tool và chỉ dẫn vào context, kể cả khi không dùng. Tắt server không cần trong /mcp.[1]
  • /clear between unrelated tasks. /clear oauth-migration names the session you're leaving so you can come back to it. For work that spans days, /rename oauth-migration in the session lets claude --resume oauth-migration pick it back up later, checkpoints included; claude --continue resumes the most recent one.[1]
  • /compact with a focus, like /compact keep the API changes and the test commands. On a long session the command is itself a big request.[1]
  • /btw answers a quick question without adding anything to the history.[3]
  • /usage shows where your usage went. On Pro, Max, Ultra, Team and Enterprise it breaks it down by skill, subagent, plugin and MCP server.[1]
  • Connected MCP servers add their tool names and instructions to the context even when unused. Turn off the ones you don't need in /mcp.[1]

Chỉnh effort thay vì viết "think hard"Set effort instead of writing "think hard"

Effort là nút chính quyết định Claude nghĩ lâu bao nhiêu. Những câu như think step by step hay be thorough chỉ là chữ bình thường trong prompt, không phải từ khóa nâng mức suy nghĩ.[1]

Effort is the main control for how long Claude thinks. Phrases like think step by step or be thorough are ordinary prompt text, not keywords that raise it.[1]

  • /effort high hoặc /effort xhigh khi dễ sót trường hợp: lỗi trong code không phải bạn viết, test lúc qua lúc không, đổi schema phải tìm mọi chỗ đọc dữ liệu cũ.
  • /effort low khi trao đổi qua lại nhanh và bạn đằng nào cũng xem từng kết quả.
  • max để dành cho bài khó muốn Claude tự làm một mình. Với việc thường, nó hay nghĩ quá mức.
  • Chỉ một câu hỏi khó giữa chừng thì thêm ultrathink vào prompt đó, không cần đổi cài đặt.[1]
  • /effort high or /effort xhigh when cases are easy to miss: a bug in code you didn't write, a flaky test, a schema change where every reader of the old shape must be found.
  • /effort low when you're going back and forth quickly and reviewing each result anyway.
  • Save max for a hard problem you want Claude to work through alone. On ordinary tasks it tends to overthink.
  • For one tricky question in the middle, put ultrathink in that prompt instead of changing the setting.[1]

Một câu vẫn có ích là be ambitious. Claude thường hiểu yêu cầu theo nghĩa hẹp và làm phần nhỏ nhất đủ đáp ứng. Câu này nói cho nó biết phạm vi bạn muốn, ví dụ cả trạng thái rỗng, trạng thái lỗi và điều hướng bằng bàn phím, chứ không chỉ layout.[1]

One phrase that still helps is be ambitious. Claude tends to read a request conservatively and build the smallest thing that satisfies it. The phrase tells it the scope you want, such as empty and error states and keyboard navigation, not just the layout.[1]

9

Dùng subagent khi có lý doUse subagents for a reason

Claude tự giao việc cho subagent khi thấy cần. Subagent đáng dùng khi bạn cần chạy song song nhiều phần việc độc lập, cần giữ output dài (cả bộ test, một lần tìm kiếm rộng) ngoài hội thoại chính, cần một người review chưa thấy code được viết thế nào, hoặc cần giới hạn tool cho một việc.[1]

Claude delegates to subagents on its own when it sees a reason. They pay off when you need independent pieces of work done in parallel, long output (a full test run, a wide search) kept out of your main conversation, a reviewer that didn't see how the code was written, or fewer tools for one task.[1]

Cái giá là token: mỗi subagent gửi request riêng và tính chung vào hạn mức của bạn. Giao cùng một việc cho subagent cũng không cho câu trả lời thông minh hơn. Một reviewer chỉ đọc, không sửa được gì, gói gọn trong một file .claude/agents/reviewer.md:[1]

The cost is tokens: each subagent sends its own requests against the same usage. Handing the same task to a subagent doesn't make the answer smarter either. A read-only reviewer that can't edit anything is one short file, .claude/agents/reviewer.md:[1]

.claude/agents/reviewer.md
---
name: reviewer
description: Reviews changed files against the spec they were built from. Use after implementing a feature, before opening the PR.
tools: Read, Grep, Glob
---
You're reviewing code you didn't write. Compare the changed files against the spec you're given,
check that every requirement is implemented and the listed edge cases have tests,
and report only the gaps that affect correctness. Skip style.

Giới hạn tools: do Claude Code thực thi, không phải lời dặn trong prompt. Việc đơn giản như gom file đang import một module thì đặt model: haiku cho subagent đó để đỡ tốn.[1]

The tools: limit is enforced by Claude Code, not requested in a prompt. For simple jobs like collecting the files that import a module, set model: haiku on that subagent to spend less.[1]

Chạy song song bằng worktree, chạy tự động bằng -pRun in parallel with worktrees, unattended with -p

Mỗi việc làm song song nên có một bản checkout riêng để các chỗ sửa không đè nhau. Lệnh sau mở một phiên trong worktree mới:[1]

Give each piece of parallel work its own checkout so the edits can't collide. This starts a session in a new worktree:[1]

$ claude -w feature-auth

Worktree là bản checkout mới, nên file bị gitignore như .env không có sẵn và dependency chưa được cài. Liệt kê chúng trong file .worktreeinclude ở gốc repo (cú pháp giống .gitignore), Claude Code sẽ chép vào mỗi worktree nó tạo. Chỉ để file nhỏ, vì đây là chép chứ không phải link.[1]

A worktree is a fresh checkout, so gitignored files like .env aren't there and dependencies aren't installed. List them in a .worktreeinclude at the repo root (same syntax as .gitignore) and Claude Code copies them into every worktree it creates. Keep it to small files, since they're copied, not linked.[1]

claude -p "prompt" chạy một lần rồi thoát, dùng được trong CI, git hook hay vòng lặp shell. Trong script, thường cần thêm: --allowedTools để duyệt trước các tool được dùng, --permission-mode dontAsk để từ chối mọi thứ khác, --max-turns để giới hạn số lượt, và --output-format json khi cần parse kết quả. Tài liệu khuyên thử trên ba file trước, sửa prompt, rồi mới chạy phần còn lại.[1]

claude -p "prompt" runs once and exits, which is how it goes into CI jobs, git hooks and shell loops. In a script you'll usually add --allowedTools to pre-approve its tools, --permission-mode dontAsk to refuse everything else, --max-turns to cap the run, and --output-format json when you need to parse the result. The docs suggest trying three files first, fixing the prompt, then running the rest.[1]

bash
for file in $(cat files.txt); do
  claude -p "Migrate $file to the new logger API and commit. Reply OK or FAIL." \
    --allowedTools "Read,Edit,Bash(git add *),Bash(git commit *)" \
    --permission-mode dontAsk \
    --max-turns 20
done

Lần nào chạm --max-turns thì lệnh thoát với lỗi thay vì trả OK hay FAIL. Ví dụ trong tài liệu có thêm --bare: cờ này bỏ qua hook, skill, plugin, MCP server và CLAUDE.md để khởi động nhanh hơn, nhưng không dùng đăng nhập claude.ai mà cần ANTHROPIC_API_KEY hoặc thông tin xác thực của nhà cung cấp cloud. Không có --bare thì mỗi vòng lặp vẫn nạp hook và CLAUDE.md của repo.[1]

A run that hits --max-turns exits with an error instead of replying OK or FAIL. The docs version adds --bare, which skips hooks, skills, plugins, MCP servers and CLAUDE.md for a faster start, but doesn't use your claude.ai login: it needs ANTHROPIC_API_KEY or your cloud provider's credentials. Without --bare, every iteration still loads the repo's hooks and CLAUDE.md.[1]
