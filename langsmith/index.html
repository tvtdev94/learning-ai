LangSmith: nhìn thấy, đo được và phát hành agent an toàn

← 1 · LangChain← 2 · LangGraph3 · LangSmith (bài này)

LangSmith là nền tảng của LangChain để quan sát (trace), đánh giá (eval), quản lý prompt và triển khai ứng dụng LLM và agent.[1] Nó không bắt buộc bạn dùng LangChain hay LangGraph.[5][6]

Bài 3/3 trong loạt LangChain · LangGraph · LangSmith. Bài 1 LangChain là framework để lắp model, tool, retriever. Bài 2 LangGraph là runtime chạy agent có state. Bài này nói về lớp nằm cạnh cả hai: ghi lại agent đã làm gì, chấm điểm nó, và đưa bản mới ra production. Khái niệm chung về tracing đã có ở trang LLM observability, về eval ở trang Đánh giá LLM. Trang này tập trung vào cách LangSmith tổ chức các việc đó.

Vì sao một nhóm làm RAG hay agent cần thứ như LangSmith?

Vấn đề 1

Không biết agent đã làm gì

Một câu trả lời sai có thể đến từ retriever, prompt, model hay tool. Trace ghi lại từng bước của một yêu cầu, từ input tới output, nên bạn thấy lỗi nằm ở bước nào.[1][2]

Vấn đề 2

Sửa chỗ này, hỏng chỗ khác

Output của LLM không tất định nên khó biết bản mới tốt hơn hay tệ hơn. Evaluation chấm điểm output trên một bộ ví dụ cố định để so sánh các phiên bản và bắt regression.[17][18]

Vấn đề 3

Lỗi gặp một lần rồi quên

LangSmith cho đưa trace thật vào dataset, để "lỗi bạn thấy một lần thành bài test chạy mỗi lần".[17]

Vấn đề 4

Production khác môi trường thử

Online evaluation chấm điểm traffic thật; dashboard và alert báo khi lỗi, độ trễ, chi phí hay điểm feedback xấu đi.[18][11][12]

LangSmith gồm những phần nào?

Observability

Ghi và xem trace

Run, trace, thread; metadata, tag, feedback; dashboard, alert, Insights; automation rule.[2][11][14]

Evaluation

Chấm điểm và so sánh

Dataset, evaluator (code, LLM-as-judge, pairwise, người chấm), experiment, annotation queue; offline trước khi phát hành và online trên production.[17][18]

Prompt & Context Hub

Quản lý prompt như mã nguồn

Lưu, đánh version, thử prompt trong Playground và đổi hành vi agent mà không phải deploy lại code.[25][26]

Agent Server · Studio

Chạy agent ở production

Runtime cho agent (trước đây tên là LangSmith Deployment) và Studio, một "IDE" để xem và debug agent.[27][29]

Không dùng LangChain có dùng được không?

Được. SDK LangSmith (giấy phép MIT) có wrap_openai và decorator @traceable để trace code bất kỳ "mà không phụ thuộc vào code LangChain nào".[5] LangSmith cũng nhận trace qua OpenTelemetry từ bất kỳ agent nào tương thích OTel,[6] và có tích hợp sẵn với nhiều framework như OpenAI, Anthropic, CrewAI, Vercel AI SDK, Pydantic AI.[1] Agent Server cũng không phụ thuộc framework.[27] Với LangChain và LangGraph thì việc bật trace dễ nhất: chỉ cần một biến môi trường.[3]

✈️ Hình dung: hộp đen và buồng tập lái

Trace giống hộp đen máy bay: ghi mọi thứ xảy ra trong một chuyến bay (một yêu cầu). Dataset là bộ bài tập tình huống khó, phần lớn rút ra từ những chuyến bay từng gặp sự cố. Experiment là cho phi công mới (phiên bản mới của agent) bay thử hết bộ bài đó trong buồng tập, có giám khảo chấm điểm (evaluator).

Chỉ khi điểm không tụt ở bài nào mới cho bay thật. Bay thật rồi vẫn có người ngồi đài kiểm soát (online evaluation, alert).

🧭 Đọc trang này theo thứ tự nào?

Mục 2 cho bạn bức tranh vòng lặp. Mục 3 đi qua từng phần. Mục 4 là một tình huống doanh nghiệp từ đầu tới cuối. Mục 5 cho bạn tự so sánh hai experiment và tự tính lượng trace phải trả tiền. Các mục sau là từ điển, bản đồ quan hệ, so sánh với công cụ khác, lỗi thường gặp và lộ trình học.

Đoạn code ngắn trên trang chỉ để minh họa khái niệm.

2. Flow: vòng lặp từ production về bài test

Tài liệu LangSmith mô tả hai kiểu đánh giá chạy ở hai giai đoạn. Offline chạy trên dataset trước khi phát hành để so sánh phiên bản và bắt regression. Online chạy trên trace thật sau khi phát hành để theo dõi chất lượng.[17] Hai phần nối thành vòng: online phát hiện vấn đề, vấn đề thành ví dụ offline, offline xác nhận bản sửa, online xác nhận production đã tốt lên.[18]

3. Cơ chế cốt lõi

3.1 Observability: dữ liệu được tổ chức thế nào

Run

Một bước việc

Một lần gọi LLM, một lần format prompt, một lần lấy tài liệu. Nếu bạn quen OpenTelemetry, run tương đương một span.[2]

Trace

Một yêu cầu

Tập các run của một thao tác, nối với nhau bằng trace ID, xếp thành cây cha–con. Mỗi trace tối đa 25.000 run; run vượt mức bị từ chối.[2]

Thread

Một cuộc hội thoại

Chuỗi trace của một phiên nhiều lượt, gom bằng metadata thread_id hoặc session_id. Key này phải có trên mọi run, kể cả run con.[2][7]

Trace nằm trong một "thùng chứa". Workspace mới trên LangSmith Cloud tổ chức theo agent: mỗi agent có bốn environment cố định là Production, Staging, Development và Local, nên trace thử nghiệm không lẫn vào số liệu production.[2][41] Workspace cũ và bản self-hosted vẫn gom trace theo tracing project; trong workspace kiểu agent, mỗi environment thực chất là một tracing project nền.[2] Cách tổ chức theo agent chỉ có trên Cloud, không có trên self-hosted.[41]

Làm giàu trace: metadata, tag, feedback

  • Tag: chuỗi để phân loại, lọc, nhóm run. Metadata: cặp key–value như phiên bản agent, môi trường, người dùng, mã tương quan nội bộ.[2][8]
  • Feedback: một điểm số gắn vào một run, gồm key và score (số liên tục hoặc nhãn). Nguồn của feedback có thể là người dùng bấm 👍/👎, người review, hay evaluator tự động.[2]
  • Metadata và tag không tự lan từ run cha xuống run con. Muốn dashboard nhóm cả trace lẫn lời gọi LLM theo một key thì phải gắn key đó ở cả hai.[11]

Một ví dụ cực ngắn để thấy "trace code bất kỳ" là gì (Python; biến môi trường LANGSMITH_TRACING=true bật/tắt trace mà không đổi code):[4]

from langsmith import traceable

@traceable(run_type="retriever")      # thành một run con
def tim_tai_lieu(cau_hoi): ...

@traceable                            # run gốc của trace
def tra_loi(cau_hoi): docs = tim_tai_lieu(cau_hoi); ...

Ghi bao nhiêu trace: sampling và conditional tracing

Mặc định mọi trace đều được ghi. Biến LANGSMITH_TRACING_SAMPLING_RATE (từ 0 tới 1) giảm số trace theo xác suất; conditional tracing bật/tắt theo logic nghiệp vụ, ví dụ tắt hẳn với khách hàng có chính sách không lưu dữ liệu.[9] Trace bị bỏ qua lúc sampling thì không còn để xem hay chấm điểm sau này.

Theo dõi: dashboard, alert, Insights, automation rule

Dashboard

Mỗi tracing project hoặc environment có dashboard dựng sẵn: số trace, độ trễ, tỉ lệ lỗi, lời gọi LLM, token và chi phí, tool, feedback. Có thể nhóm theo tag hoặc metadata, hoặc tự dựng dashboard riêng.[11]

Alert

Cảnh báo theo ngưỡng trên số run, chi phí, lỗi (số lượng hoặc tỉ lệ), điểm feedback trung bình, độ trễ. Gửi tới Slack, PagerDuty, Dynatrace hoặc webhook. Mỗi alert gắn với một project hoặc một environment.[12]

Insights và Engine

Insights tự phân nhóm trace để thấy người dùng hỏi gì và agent hỏng kiểu gì (gói Plus, Enterprise).[13] Engine đi xa hơn: gom lỗi lặp lại thành "issue", chẩn đoán nguyên nhân, đề xuất sửa và tạo example cho dataset.[36]

Automation rule

Một rule gồm item type (run hay thread), filter, sampling rate và action: thêm vào dataset, đưa vào annotation queue, gọi webhook, chạy evaluator, gia hạn lưu trữ. Ví dụ: mọi trace có feedback xấu → annotation queue.[14]

3.2 Evaluation: dataset, evaluator, experiment

Ba khái niệm trung tâm:[18]

  • Dataset là tập example. Mỗi example có inputs, reference outputs (đáp án mẫu, tùy chọn, chỉ evaluator nhìn thấy, app thì không) và metadata.
  • Evaluator chấm điểm và trả về feedback gồm key, score hoặc value, và comment giải thích. Evaluator là tài nguyên cấp workspace, gắn được vào nhiều dataset và project.
  • Experiment là kết quả chạy một phiên bản của app trên một dataset: output, điểm và trace của từng example. Nhiều experiment trên cùng dataset thì so sánh được với nhau.

So sánh experiment và chặn regression

Chọn hai experiment trở lên trên cùng dataset rồi bấm Compare. Một experiment được đặt làm source (mốc). Ô màu đỏ là example bị tụt điểm so với mốc, ô màu xanh là example tốt lên; đầu mỗi cột cho biết bao nhiêu example tốt lên hay xấu đi. Mặc định điểm cao là tốt, đổi được cho từng key.[21]

Để biến evaluation thành cổng kiểm soát trong CI, có plugin pytest (và bản Vitest/Jest cho JS/TS): mỗi test là một example, assertion fail thì CI fail.[24] Khi chạy trong CI nên bật cache để bớt lời gọi LLM và chi phí.[19] Tài liệu phân biệt: evaluation đo theo metric, testing khẳng định đúng hay sai; regression test chính là biến metric thành điều kiện bắt buộc.[18]

Annotation queue: người chấm có quy trình

Single-run queue đưa từng run hoặc thread cho người review chấm theo rubric, ghi chú, và viết assertion (tiêu chí chấp nhận) để lưu thành output mong đợi của example. Pairwise queue đặt hai run cạnh nhau để chọn A tốt hơn, B tốt hơn, hay ngang nhau. Có thể đặt số người review cho mỗi item, và cơ chế giữ chỗ để hai người không chấm trùng.[23]

Online evaluator

Gắn evaluator vào project hoặc environment production; lọc trace cần chấm (vd. trace có feedback xấu, trace gọi một tool cụ thể, khách hàng gói enterprise) và đặt sampling rate, vd. 0,1 để chỉ chấm 10% trace cho đỡ tốn. Có thể chấm lại trace cũ (backfill) lúc tạo rule, và đặt hạn mức chi tiêu theo tuần cho evaluator.[22] Xem thêm khái niệm chung ở Đánh giá LLM.

3.3 Prompt & Context Hub và Playground

Tên hiện tại trong tài liệu là Prompt & Context Hub: nơi lưu, đánh version và cập nhật prompt và "context" (gói hướng dẫn và tool định nghĩa một skill hoặc cả agent). Mục tiêu là đổi hành vi agent mà không cần deploy lại, và để người hiểu nghiệp vụ tự sửa phần họ nắm rõ nhất.[26]

  • Mỗi lần lưu prompt tạo một commit có hash riêng; code có thể ghim đúng commit.[25]
  • Commit tag là nhãn dời được sang commit khác, nên đổi phiên bản mà không sửa code. Tag staging và production dành riêng cho tính năng Environments.[25]
  • Playground cho đổi model, prompt, output schema, tool, nhập biến rồi chạy thử; chạy cả một dataset thì ra một experiment.[25] Prompt của evaluator LLM-as-judge tạo trong UI cũng được tự lưu vào prompt hub.[22]

Cách viết prompt tốt nằm ở trang Prompt engineering; ở đây chỉ nói chỗ lưu và cách quản lý phiên bản.

3.4 Agent Server và Studio

Tên sản phẩm đã đổi hai lần: LangGraph Platform → LangSmith Deployment (tuần 20–24/10/2025) → LangSmith Agent Server (11/2026).[44][30][27] Bài 2 đã nói chi tiết về runtime này; tóm tắt lại:

  • Agent Server là runtime điều phối cho agent: có assistant (agent đã cấu hình), thread (state), run (một lần chạy), cron job; lưu dữ liệu trong PostgreSQL; dùng Redis cho hàng đợi và streaming.[28]
  • Graph không bắt buộc viết bằng LangGraph; agent của framework khác được bọc lại để deploy.[28] Trang Deploy có 4 lựa chọn: Cloud (gói Plus trở lên), Hybrid, Self-hosted kèm control plane (Enterprise), và Standalone server tự mang PostgreSQL, Redis và license. Nếu LangSmith của bạn chạy kiểu BYOC thì Agent Server cũng chạy được ở đó.[27][31]
  • Ở Hybrid, Agent Server chạy trong hạ tầng của bạn và gửi trace lên LangSmith Cloud hoặc LangSmith tự host.[37]
  • Studio là IDE cho agent: xem kiến trúc graph, chạy thử, quản lý assistant và thread, sửa prompt, chạy experiment trên dataset, debug bằng time travel, deploy lên Cloud bằng một cú bấm. Studio làm việc với server chạy ở máy hoặc đã deploy.[29]
Hai lựa chọn tách rời. Nơi agent chạy (Agent Server) và nơi đặt LangSmith để trace và eval là hai quyết định riêng.[27] Bạn có thể chạy agent trên hạ tầng sẵn có và chỉ gửi trace lên LangSmith ("observability only").[31]

GCP US, GCP EU, GCP APAC, AWS US, Azure US, mỗi vùng có hostname riêng. Chưa hỗ trợ chuyển tổ chức sang vùng khác, nên chọn vùng từ đầu. Trang FAQ ghi LangSmith tuân thủ GDPR, có SOC 2 Type 2 và tuân thủ HIPAA.[32]

Thời gian lưu trace

Mỗi trace thuộc một trong hai mức: base hoặc extended. Trên Cloud: base 14 ngày, extended 180 ngày; BYOC và self-hosted mặc định 14 và 400 ngày. Hết hạn là trace bị xóa. Muốn giữ lâu thì đưa vào dataset: dataset không hết hạn.[15][2]

Che dữ liệu nhạy cảm

Che trước khi gửi lên: ẩn hẳn input/output bằng biến môi trường, dùng anonymizer theo regex, hoặc dùng Microsoft Presidio, Amazon Comprehend để tìm PII. Với khách hàng không cho lưu dữ liệu, nên tắt trace cho các yêu cầu đó (conditional tracing).[10]

Phân quyền

RBAC (vai trò theo workspace, vai trò tùy chỉnh) là tính năng Enterprise; gói khác mặc định mọi người là Admin. ABAC (Enterprise) thu hẹp quyền theo tag của tài nguyên hoặc metadata của trace, vd. chỉ cho xem trace của phòng ban mình.[34][35] Xem thêm trang Governance.

Trace tự lên extended. Trace sẽ tự được nâng lên extended (giữ lâu hơn, tính thêm phí) khi: một online evaluator chấm nó, một automation rule có bật gia hạn khớp với bất kỳ run nào trong nó, hoặc feedback gửi qua API có cờ extend_trace_retention=true. Gia hạn được bật mặc định cho evaluator và rule mới. Feedback bấm trong UI và việc thêm thủ công vào annotation queue thì không nâng. Run của experiment được tạo sẵn ở mức extended.[15] Theo giá niêm yết ở mục 3.6, phí nâng chỉ bằng một nửa giá base của trace đó, nên khoản lớn nhất của hóa đơn thường là số trace được ghi: sampling là đòn bẩy chính, extended là phần cộng thêm.[16] Mục 5.2 cho bạn tự tính.

Muốn đưa trace ra kho dữ liệu riêng (BigQuery, Snowflake…) thì có bulk export sang bucket S3-compatible dạng Parquet; với khách đăng ký sau 03/08/2026, tính năng này chỉ có ở gói Enterprise.[43]

4. Ví dụ đi qua từng bước: trợ lý nội bộ trả lời sai số ngày phép

Tình huống: Công ty Thành Đạt (giả định) có "Trợ lý Nội bộ", một agent RAG viết bằng LangGraph, trả lời nhân viên về chính sách nhân sự, IT và tài chính dựa trên kho văn bản nội bộ. Tên công ty, người, câu hỏi, con số là minh họa. Tính năng và cơ chế ở từng bước theo tài liệu LangSmith. Phần RAG nền tảng xem ở trang RAG, phần agent ở trang AI agent.

5. Mô phỏng

5.1 So sánh hai experiment trên dataset của Trợ lý Nội bộ

Baseline là bản đang chạy: retriever không lọc văn bản hết hiệu lực, prompt không yêu cầu trích nguồn, model lớn. Bạn bật/tắt các thay đổi cho bản ứng viên (candidate). Trình duyệt sinh output của từng phiên bản theo luật cố định, rồi chạy thật hai evaluator kiểu code trên output đó: correctness (output có chứa đáp án mẫu không) và citation (có trích nguồn không). Cổng phát hành chặn nếu có example bị tụt correctness.

Dataset, output và độ trễ là minh họa. Trong thực tế correctness của câu trả lời tự do thường cần LLM-as-judge; ở đây dùng so khớp chuỗi cho dễ kiểm tra. Cách tô đỏ/xanh theo comparison view của LangSmith.[21]

Câu hỏi tự kiểm tra

1. Run, trace và thread khác nhau thế nào?

Run là một bước việc (một lời gọi LLM, một lần lấy tài liệu). Trace là tập run của một yêu cầu, xếp thành cây. Thread là chuỗi trace của một cuộc hội thoại nhiều lượt, gom bằng metadata thread_id hoặc session_id.[2][7]

2. Vì sao evaluator "đúng so với đáp án" không chạy được online?

Vì traffic thật không có reference output. Online chỉ dùng được evaluator reference-free như kiểm an toàn, định dạng, hoặc LLM-judge chấm độ bám ngữ cảnh.[18]

3. Experiment là gì, và comparison view cho bạn thấy gì?

Experiment là kết quả chạy một phiên bản app trên một dataset. Comparison view đặt nhiều experiment cạnh nhau, tô đỏ example tụt điểm và xanh example tốt lên so với experiment mốc (source).[18][21]

4. Ba hành động nào làm trace tự lên mức extended? Hành động nào thì không?

Có nâng: online evaluator chấm trace (khi bật gia hạn), automation rule có bật gia hạn khớp một run trong trace, feedback qua API có extend_trace_retention=true. Không nâng: feedback và ghi chú trong UI, thêm thủ công vào annotation queue.[15]

5. Muốn giữ một trace hay quá 14 ngày thì làm gì?

Thêm input/output của nó vào dataset (dataset không hết hạn), hoặc nâng trace lên extended.[2][15]

6. Không dùng LangChain thì trace bằng cách nào?

Dùng SDK LangSmith (@traceable, wrap_openai), integration có sẵn của framework bạn dùng, hoặc gửi qua OpenTelemetry.[5][6][2]

7. Agent Server hiện tên là gì, và trước đây tên gì?

LangSmith Agent Server (từ 11/2026); trước đó là LangSmith Deployment (từ 10/2025), trước nữa là LangGraph Platform.[30][44]

8. Dữ liệu không được rời VPC công ty thì có những lựa chọn nào với LangSmith?

BYOC (LangChain vận hành control plane, data plane trong VPC của bạn) hoặc self-hosted; cả hai thuộc gói Enterprise. Với phần chạy agent, có thể dùng Hybrid hoặc self-hosted Agent Server.[31][33][27]

9. Sampling và conditional tracing khác nhau ở đâu?

Sampling bỏ ngẫu nhiên một phần trace để giảm lượng; conditional tracing bật/tắt chắc chắn theo điều kiện nghiệp vụ, như tắt trace cho khách không cho lưu dữ liệu.[9]

10. Vì sao nên kiểm LLM-as-judge với điểm của người trước khi dùng nó để chặn phát hành?

Tài liệu ghi LLM-as-judge cần xem lại điểm và chỉnh prompt; có thể đưa điểm người sửa vào làm few-shot để judge sát với người hơn.[18][20]
